# AGENTS.md

## 1. Purpose of this file

This file is the operating manual for coding agents, contributors, and maintainers working in this repository. Read it before making changes. It explains the product, architecture, data model, conventions, API behavior, testing rules, risk areas, and the preferred way to extend the application.

The goal is to keep the codebase simple, predictable, and safe to modify even when work is performed by different people or automated coding agents over time.

---

## 2. Product overview

**Product name:** Focusboard

**Product type:** Lightweight personal productivity web application

**Core jobs to be done:**

1. Capture tasks quickly.
2. Track what is active, completed, overdue, and high priority.
3. Add lightweight context to tasks through descriptions, categories, priorities, and due dates.
4. Capture longer-form notes that should remain available beside the task list.
5. Search and filter both tasks and notes without requiring a database or account system.
6. Remain easy to run locally with the smallest reasonable dependency footprint.

This is intentionally a small application. Avoid turning it into a large framework-heavy product unless a future requirement clearly justifies that change.

## 3. Current feature set

### Todos

A todo contains:

- `id`: UUID generated by the server.
- `title`: required short text.
- `description`: optional longer text.
- `priority`: one of `low`, `medium`, or `high`.
- `dueDate`: optional ISO timestamp.
- `category`: optional short text label.
- `completed`: boolean.
- `createdAt`: ISO timestamp.
- `updatedAt`: ISO timestamp.
- `completedAt`: ISO timestamp or `null`.

Supported todo behavior:

- Create.
- Edit.
- Complete and reopen.
- Delete.
- Search title, description, and category.
- Filter by active/completed state.
- Filter by priority.
- Sort by creation date or due date.
- Display overdue state when applicable.

### Notes

A note contains:

- `id`: UUID generated by the server.
- `title`: required short text.
- `content`: note body.
- `tag`: optional short text label.
- `pinned`: boolean.
- `createdAt`: ISO timestamp.
- `updatedAt`: ISO timestamp.

Supported note behavior:

- Create.
- Edit.
- Pin and unpin.
- Delete.
- Search title, content, and tag.
- Filter to pinned notes.
- Show pinned notes first, then order by latest update.

### Dashboard and usability features

- Active todo count.
- Completed todo count.
- Overdue todo count.
- Total note count.
- Dark/light theme preference stored in browser `localStorage`.
- Responsive layout.
- API health endpoint.

## 4. Technology stack

### Server

- Node.js 20 or later.
- Express 5.
- CommonJS modules.
- Node built-in modules for file access, UUID generation, HTTP test server, and tests.

### Client

- Plain HTML.
- Plain CSS.
- Plain browser JavaScript.
- Native Fetch API.
- No frontend framework.
- No build step.

### Persistence

- JSON file at `data/db.json`.
- Writes are serialized through an in-process promise chain.
- Writes are performed through a temporary file and rename operation to reduce the chance of partially-written JSON.

### Tests

- Node's built-in `node:test` runner.
- Native Fetch API against an ephemeral HTTP server.
- No test framework dependency is currently required.

### File responsibilities

#### `server.js`

Production/runtime entry point. It creates the Express app and binds it to the configured port.

Keep this file very small. Application configuration should generally live in `src/app.js`, not here.

#### `src/app.js`

Express composition root.

Responsibilities:

- Create the Express app.
- Resolve the data file or injected store.
- Configure JSON parsing.
- Mount API routers.
- Serve static frontend files.
- Provide API fallback handling.
- Provide final server error handling.

Do not put endpoint-specific business logic here.

#### `src/services/store.js`

Persistence abstraction.

Responsibilities:

- Ensure the JSON data file exists.
- Read and parse JSON data.
- Return normalized top-level collections.
- Serialize writes.
- Use temp-file replacement for safer writes.
- Generate UUIDs.

The current store is appropriate for a local/single-instance app. It is **not** a substitute for a transactional database in a multi-instance production deployment.

#### `src/routes/todos.js`

Todo HTTP API.

Responsibilities:

- Parse query filters.
- Validate create/update payloads.
- Build todo domain objects.
- Read/write todo data through the store.
- Return appropriate HTTP status codes.

#### `src/routes/notes.js`

Note HTTP API with the same general responsibilities as the todo router.

#### `src/routes/stats.js`

Read-only derived metrics for the sidebar/dashboard.

Do not persist stats separately. They are derived from current todos and notes.

#### `src/utils/validation.js`

Central request validation and string normalization.

Keep allowed enum values, maximum lengths, and field parsing rules here so route files do not duplicate validation logic.

#### `public/index.html`

Single-page UI shell and semantic form structure.

No template engine is used. The server serves this file as static content.

#### `public/styles.css`

All application styles, including responsive behavior and theme variables.

Prefer the existing CSS custom properties over hard-coded duplicate values.

#### `public/app.js`

Browser-side application controller.

Responsibilities:

- Fetch data from the API.
- Manage lightweight UI state.
- Render tasks and notes.
- Wire form submission.
- Wire filters and search.
- Edit/delete/toggle/pin actions.
- Escape user-generated text before inserting HTML.
- Persist theme choice in `localStorage`.

Do not move authoritative business rules to the browser. The server must still validate all API input.

#### `tests/api.test.js`

Integration-style API tests using a temporary data file and an ephemeral local HTTP server.

Tests should never depend on or modify the repository's real `data/db.json`.

## 7. API contract

All API payloads use JSON unless the response has no body.

### Health

#### `GET /api/health`

Response:

```json
{
  "status": "ok",
  "timestamp": "2026-01-01T12:00:00.000Z"
}
```

### Todos

#### `GET /api/todos`

Optional query parameters:

- `status=active|completed`
- `priority=low|medium|high`
- `category=<string>`
- `q=<search string>`
- `sort=created-desc|created-asc|due-asc|due-desc`

Response shape:

```json
{
  "todos": []
}
```

#### `POST /api/todos`

Example request:

```json
{
  "title": "Finish project brief",
  "description": "Add scope and acceptance criteria",
  "priority": "high",
  "dueDate": "2026-10-01T09:00:00.000Z",
  "category": "Work",
  "completed": false
}
```

The only required user-provided field is `title`. Server defaults fill the remaining optional fields.

Success: `201 Created`.

Validation failure: `400 Bad Request` with:

```json
{
  "errors": ["Title is required."]
}
```

#### `PATCH /api/todos/:id`

Accepts any subset of editable todo fields.

Success: `200 OK`.

Unknown todo: `404 Not Found`.

When `completed` becomes true, `completedAt` is populated. When a completed item is reopened, `completedAt` becomes `null`.

#### `DELETE /api/todos/:id`

Success: `204 No Content`.

Unknown todo: `404 Not Found`.

### Notes

#### `GET /api/notes`

Optional query parameters:

- `q=<search string>`
- `tag=<exact tag, case-insensitive>`
- `pinned=true`

Response shape:

```json
{
  "notes": []
}
```

#### `POST /api/notes`

Example request:

```json
{
  "title": "Launch ideas",
  "content": "Use the waitlist as an interview pool.",
  "tag": "Idea",
  "pinned": true
}
```

`title` is required. New notes also expect meaningful content; validation currently rejects empty content on creation.

Success: `201 Created`.

#### `PATCH /api/notes/:id`

Accepts any subset of editable note fields.

Success: `200 OK`.

#### `DELETE /api/notes/:id`

Success: `204 No Content`.

### Stats

#### `GET /api/stats`

Response shape:

```json
{
  "todos": {
    "total": 0,
    "active": 0,
    "completed": 0,
    "overdue": 0
  },
  "notes": {
    "total": 0,
    "pinned": 0
  }
}
```

## 8. Validation and domain rules

### General rules

- User-controlled strings are trimmed on the server.
- Maximum string lengths are enforced by server validation.
- Browser constraints such as `maxlength` are conveniences only and must not replace server validation.
- Unknown extra request fields are ignored rather than persisted.
- IDs are generated server-side.
- Timestamps are generated server-side.
- API routes return structured JSON errors.

### Todo rules

- Title: required, maximum 160 characters.
- Description: maximum 2,000 characters.
- Category: maximum 60 characters.
- Priority: `low`, `medium`, or `high` only.
- Due date: empty/null or parseable date input.
- Completed: boolean only.

### Note rules

- Title: required, maximum 160 characters.
- Content: maximum 10,000 characters; required on note creation.
- Tag: maximum 60 characters.
- Pinned: boolean only.

When extending the model, update server validation first, then routes, tests, frontend form/rendering, README/API docs, and this file.

## 9. Data persistence model

The data file has this top-level structure:

```json
{
  "todos": [],
  "notes": []
}
```

### Important persistence constraints

1. Do not manually change this structure without updating `JsonStore.read()` normalization and the routes that consume it.
2. Do not write directly to `data/db.json` from route handlers; use the store.
3. Keep writes serialized through the store to avoid overlapping in-process writes.
4. Keep atomic temp-file replacement unless there is a well-tested reason to change it.
5. Treat `data/db.json` as local application state, not as source code.

### Known limitations

The JSON store is intentionally simple and has limitations:

- It is not suited for several server processes writing concurrently.
- It does not provide transactions across independent processes.
- Large datasets will become inefficient because whole collections are read and written.
- It is not intended for sensitive multi-user production data.

If the project grows, a logical migration path is SQLite first, then a server database such as PostgreSQL when multi-user or hosted production requirements justify it.

## 10. Frontend implementation rules

### Rendering safety

Any user-provided value inserted into an HTML string must go through `escapeHtml()`.

Do not add raw user strings to `innerHTML` without escaping them.

Values assigned directly through form element `.value` properties do not need HTML escaping because they are not interpreted as markup.

### State ownership

The server/API is the source of truth.

The browser keeps only transient snapshots in the `state` object. After mutations, refresh the relevant server-backed list and stats instead of trying to maintain a complicated parallel local model.

### Search

Search requests are debounced slightly to avoid a request for every keystroke. Keep search responsive without adding unnecessary client complexity.

### Theme

Theme is a local user preference and is therefore stored in `localStorage`. It does not need server persistence in the current single-user architecture.

### Accessibility expectations

When changing the UI:

- Preserve form labels.
- Preserve keyboard-usable native controls.
- Give checkboxes accessible labels.
- Keep visible focus states.
- Do not encode status using color alone.
- Keep sufficient foreground/background contrast.
- Maintain sensible heading hierarchy.

## 11. Server implementation rules

### Routing

Use one router per domain area. If a new domain becomes substantial, add another file under `src/routes/` instead of making `src/app.js` large.

### Error handling

Expected client errors should be returned explicitly from routes as 4xx responses.

Unexpected errors should be passed to Express error middleware with `next(error)`.

Do not expose stack traces or raw filesystem error details in API responses.

### Status code expectations

- `200`: successful read or update.
- `201`: successful creation.
- `204`: successful deletion with no response body.
- `400`: validation/input error.
- `404`: requested domain object or API route not found.
- `500`: unexpected server failure.

### Security basics

The app already disables the `X-Powered-By` header.

Future security-sensitive work should consider:

- Rate limiting if exposed publicly.
- Helmet or equivalent response headers.
- Authentication before supporting multiple users or private hosted data.
- CSRF strategy if cookie-based authentication is later added.
- Request body limits for any new large-content endpoint.
- Database parameterization if/when SQL is introduced.

Do not add authentication superficially. A partial or insecure auth system is worse than clearly documenting that this version is single-user/local-first.

## 12. Testing expectations

Every behavior change should have an appropriate test when practical.

Current tests cover:

- Todo creation.
- Todo update/completion.
- Todo filtering.
- Todo deletion.
- Note creation.
- Note pinning.
- Todo validation failures.

### Add tests when changing

- Validation rules.
- API status codes.
- Route filtering or sorting.
- Completion timestamp behavior.
- Persistence behavior.
- New endpoints.
- Any bug that could reasonably regress.

### Test isolation rule

Tests must create a temporary data location and clean it up.

Never point automated tests at `data/db.json`.

### Preferred test style

Prefer black-box HTTP assertions against the Express app because they test routing, JSON parsing, validation, and response behavior together.

Unit tests are also acceptable for isolated helpers when they make failures clearer.

## 13. Coding style and conventions

### JavaScript

- Use `const` by default; use `let` only when reassignment is required.
- Use semicolons consistently.
- Prefer small functions with a single clear responsibility.
- Prefer early returns for validation and not-found cases.
- Use `async`/`await` for asynchronous control flow.
- Avoid deeply nested promise chains.
- Keep CommonJS (`require`, `module.exports`) unless intentionally migrating the whole project.
- Do not mix module systems casually.

### Naming

- Functions: verbs or verb phrases (`loadTodos`, `validateNoteInput`).
- Boolean fields: adjectives/state terms (`completed`, `pinned`).
- Router factory functions: `createXRouter`.
- File names: lowercase, descriptive nouns where possible.

### Comments

Do not narrate obvious syntax. Comments should explain decisions, constraints, unusual behavior, or non-obvious edge cases.

### Dependencies

The project intentionally has a tiny dependency footprint.

Before adding a package, ask:

1. Can the platform or existing code do this simply already?
2. Does this dependency solve enough complexity to justify maintenance and security surface?
3. Is the package actively maintained?
4. Is it needed in production or only development?

Do not add a frontend framework just to implement small UI interactions.

## 15. Change checklist for coding agents

Before editing:

1. Read this file and the relevant source files.
2. Identify the smallest layer(s) that need to change.
3. Confirm whether the change affects the data model or API contract.
4. Avoid unrelated cleanup unless it directly reduces risk for the requested change.

While editing:

1. Keep server validation authoritative.
2. Keep frontend rendering escaped.
3. Preserve existing API behavior unless the task intentionally changes it.
4. Update tests alongside meaningful behavior changes.
5. Keep persistence changes backwards-aware when feasible.

Before finishing:

1. Run `npm run check`.
2. Run `npm test`.
3. Manually inspect any UI change at desktop and narrow viewport sizes when browser tooling is available.
4. Confirm the main flows still work: create, edit, complete/pin, filter/search, delete.
5. Update README and this file if commands, architecture, API, or conventions changed.
6. Summarize changed files and any known limitations.

- Syntax checks pass.

## 17. Agent-specific guardrails

Automated coding agents should follow these additional rules:

- Do not delete user data from `data/db.json` as part of routine refactoring.
- Do not rewrite the project into another framework unless explicitly requested.
- Do not add authentication, a database, TypeScript, a frontend framework, Docker, or a build tool merely because they are common choices.
- Do not silently change API field names.
- Do not change timestamp semantics without tests and documentation.
- Do not trust browser validation; preserve server validation.
- Do not expose filesystem paths, stack traces, or internal exceptions to clients.
- Do not store derived stats when they can be calculated from primary data.
- Do not use destructive migrations without a backup/migration strategy.
- Do not run tests against the real application data file.
- Do not embed secrets in code, `.env.example`, documentation, or test fixtures.
- Do not use `innerHTML` with unescaped user content.

If a requested change conflicts with these guardrails, prefer preserving correctness and data safety, and document the conflict clearly.

If you are new to this repository, the shortest accurate mental model is:

- `src/app.js` wires the app together.
- `src/routes/*` defines the API.

## 26. Production Deployment and Hosting

### 26.1 Current recommended host: Railway

For the current JSON-backed architecture, Railway is the preferred deployment target because the application needs a persistent filesystem location for `db.json`. A Railway Volume should be attached to the web service.

Production topology:

```text
Internet
   |
   v
Railway Public Domain
   |
   v
Node.js / Express service
   |
   v
DATA_FILE=/data/db.json
   |
   v
Railway Volume mounted at /data
```

### 26.2 Deployment-related files

The repository includes `railway.json`. It defines:

- Railpack as the builder.
- `npm start` as the production start command.
- `/api/health` as the deployment health-check endpoint.
- A finite restart policy for failed processes.

Do not remove the health endpoint without updating `railway.json` and the deployment platform configuration.

### 26.3 Runtime environment contract

The application recognizes these environment variables:

- `PORT`: HTTP port supplied by the hosting platform. Falls back to `3000` locally.
- `HOST`: listener address. Falls back to `0.0.0.0` so the server is reachable in a container/PaaS environment.
- `DATA_FILE`: absolute or relative path for the JSON datastore. Falls back to `./data/db.json` for local development.

On Railway, use:

```text
DATA_FILE=/data/db.json
```

and mount the persistent Volume at:

```text
/data
```

### 26.4 Persistence warning

Never assume a cloud service's root filesystem is durable. The production datastore must live inside a persistent volume, or the application must be migrated to a managed database.

If an agent changes the storage layer, it must update:

1. `src/services/store.js` or its replacement.
2. `src/app.js` dependency initialization.
3. Tests.
4. `.env.example`.
5. `README.md` deployment instructions.
6. This `AGENTS.md` section.

### 26.5 Scaling limitation of the JSON architecture

The JSON datastore is intentionally simple and suitable for this single-instance project. It should not be horizontally scaled to multiple application replicas that concurrently write the same file. File-level persistence is not a substitute for a transactional multi-user database.

Before introducing multiple replicas, authentication for many independent users, background workers that mutate data, or high write concurrency, migrate persistence to a database such as PostgreSQL.

### 26.6 Deployment verification checklist

After every production deployment, verify all of the following:

- `GET /api/health` returns HTTP 200.
- The main page loads through HTTPS.
- A todo can be created.
- The todo persists after a browser refresh.
- A note can be created and pinned.
- A todo can be completed and reopened.
- Search/filter controls still work.
- The app can be restarted or redeployed without losing previously saved data.
- No stack traces or sensitive environment values appear in browser responses.
- Static assets load successfully.

### 26.7 Custom domains

A custom domain can be attached at the hosting-platform level without changing application routes. Keep the application origin-agnostic unless a future feature requires an explicit public base URL.

If future authentication, OAuth, email links, webhooks, or absolute callback URLs are introduced, add a `PUBLIC_BASE_URL`-style environment variable instead of hard-coding a deployment domain.

### 26.8 Future database migration path

When the project outgrows a JSON file, prefer PostgreSQL. Preserve the existing API contract so the frontend does not need to be rewritten merely because persistence changes.

A sensible migration sequence is:

1. Introduce a storage/repository interface matching the operations currently provided by `JsonStore`.
2. Implement a PostgreSQL-backed repository.
3. Add schema migrations for todos and notes.
4. Update tests to run against isolated test data.
5. Switch production configuration to `DATABASE_URL`.
6. Keep `JsonStore` available for lightweight local development only if it remains useful.

Do not mix direct SQL calls into Express route handlers. Keep persistence concerns behind a dedicated data-access layer.
